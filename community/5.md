玩家互传（TPA）让任意两名玩家互相发起传送请求：一方在菜单里选中目标玩家，另一方抬头同意即可传送，低头或超时则取消。本文档整理自原作者分享的命令组，并补充了原理解释。

> 如果你只需要「发起 → 接受 → 传送」的简化版，可参考 [`/docs/community/3/`](../3/)（雪球菜单）中的发起/接受传送部分。

### 原理解释

**三个核心状态**

- `传送菜单`（菜单状态机）—— 记录每位玩家「当前在菜单里做什么」：
  - `40` = 菜单基态（已打开、未选中任何行）
  - `41`~`50` = 正在浏览列表第 1~10 行
  - `51` = 选中「刷新列表」
  - `100` = 已被选为传送目标（等待回应）
  - `101` = 已接受请求（接受方）
  - `1000`+ = 取消/超时标记，`2000` = 清理标记
  - `5` = 从上级菜单选中「互传」后的入口状态（指令 1 把它归位成 `40`）

- `传送`（配对 ID）—— 每位玩家的「槽位号」：
  - `0`~`39` = 在线玩家的列表编号（第 0 位、第 1 位……）
  - `40`+ = 已发起请求的玩家（持有正槽位）
  - `-40`- = 等待回应的目标（持有负槽位）

  发起方和目标持有**同一个槽位号**，只是目标取反：谁把正负相加抵消成 `0`，谁就是发起方，用这一个数记住「谁和谁是一对」。

- `rx`/`rxm`（视角）—— 抬头 `rx=-88` = 确认/选择，低头 `rxm=88` = 拒绝/取消，与 [`雪球菜单`](../3/) 一致。

**+41 位移技巧**

列表第 1 行对应 `传送菜单=41`，而这一行玩家的槽位号是 `0`，中间正好差 41。选择时先 `add @a 传送 41`（指令 7）把所有人整体 +41，于是第 N 行玩家的槽位临时变成 `41+N`，恰好等于他的 `传送菜单`。这样就能用 `if score @s 传送 = @s 传送菜单` 判断「选的是不是自己」（指令 8），用 `if score @s 传送 = @p[...] 传送菜单` 找出被点中的目标（指令 9~11）。判断完 `remove @a 传送 41`（指令 13）还原。

**配对与接受**

发起请求后：目标从 `互传记录` 领一个新槽位（指令 14），发号器 +1（指令 15），发起方抄下同一个槽位（指令 16），目标再取反为负（指令 18）。接受时目标抬头 → `传送菜单=101`（指令 41），把目标的负槽位加到所有人（指令 42）：发起方的正槽位被抵消成 `0`，于是 `tp @a[scores={传送=0}]` 精确命中发起方并传送到目标（指令 43），最后用相反操作撤销（指令 46）。

**为什么用「假玩家」计数器**

`互传记录`（配对发号器，从 40 起发）、`负`（常量 -1，用于取反）、`检测`/`在线人员`/`互传`（一致性检查）。其中 `在线人员` 每刻统计当前在线人数，与上一刻的基准 `互传` 比较：人数一旦变化就清理离线玩家残留的配对，随后把 `互传` 更新为最新值（指令 28）。用假玩家（fake player）而不是实体，是因为它们永远存在、不占实体，且分数能直接参与 `scoreboard players operation` 运算。

### 前置指令

在聊天栏中依次执行（创建计分板与常量）：

```
/scoreboard objectives add 传送菜单 dummy
/scoreboard objectives add 传送 dummy
/scoreboard players set 负 传送 -1
/scoreboard players set 互传记录 传送 40
```
```
/gamerule commandblockoutput false
```
```
/gamerule sendcommandfeedback false
```

> `负` 是常量 -1（用于取反标记）；`互传记录` 是配对槽位发号器，从 40 起发，避免与列表编号 0~39 冲突。

本组指令是原作者「织梦菜单」系统的互传模块，有两处依赖上级菜单，独立使用前需先补齐：

1. **入口**——玩家以 `传送菜单=5` 的状态进入本菜单（指令 1 负责把它归位）。独立使用时需要自行设计一个触发器把玩家的 `传送菜单` 设为 `5`（例如投掷雪球时 `scoreboard players set @p 传送菜单 5`）。
2. **列表槽位**——玩家列表按每位玩家的 `传送` 槽位号 0~39 排序显示，需保证在线玩家持有互不重复的编号。参考实现见文末「常见问题」。

### 命令方块摆放

按分组顺序摆放：每组以**循环**命令方块开头（每游戏刻持续监测），其余用**连锁**命令方块按箭头方向连接、在同一游戏刻内跟随执行。所有条件判断都写在 `execute` 的 `if`/`unless` 里，因此无需「有条件」命令方块。

### 常见问题

<details>
<summary>为什么「自己传自己」会被拒绝？</summary>

指令 8 用 `if score @s 传送 = @s 传送菜单` 检测选中行是否对应自己，若为自己则提示「不可以向自己申请互传」。这是通过 +41 位移后比较「自己的槽位」与「自己的光标」实现的。

</details>

<details>
<summary>为什么点列表没反应 / 提示玩家不存在？</summary>

通常是「列表槽位」没维护好：列表按每位玩家的 `传送` 槽位号（0~39）排序显示，若所有人都停在 `传送=0`，列表只会显示第一行、无法选中他人。请先按下面的方法给在线玩家分配互不重复的槽位号。

</details>

<details>
<summary>如何给玩家分配列表槽位？</summary>

原系统的列表编号由上级「织梦菜单」统一发号。独立使用时，可加两个循环命令方块，每刻给最近一个「尚未分配」的玩家发下一个编号：

```
<CmdRepeat>`/execute as @p[scores={传送=0}] run scoreboard players operation @s 传送 = 列表编号 传送`
<CmdRepeat>`/execute as @p[scores={传送=0}] run scoreboard players add 列表编号 传送 1`
```

并把 `列表编号` 初始化为 1：

```
/scoreboard players set 列表编号 传送 1
```

注意：`传送=0` 被当作「待分配」的初始值，因此 0 号不会被真正分配出去，列表实际从 1 号开始显示（第一行留空属正常现象）。玩家离线的槽位不会自动回收，长期运行需结合指令 21~23 的一致性检查做清理。

</details>

<details>
<summary>离线玩家会残留导致列表错乱吗？</summary>

系统用 `检测`/`在线人员` 两个假玩家计数做一致性检查：槽位 0 重复、在线人数变化时，把受影响玩家的 `传送` 标记为 -1 并扣除修正（指令 19~27），随后指令 28 把在线人数基准 `互传` 更新为最新值，供下一轮比较。

</details>

<details>
<summary>标题里的「织梦菜单」能改吗？</summary>

可以，那是原作者的菜单名，纯展示文案。把指令 4 里的 `织梦菜单` 替换成你服务器的名字即可，不影响逻辑。

</details>

### 基岩版注意

- 全部为基岩版语法：`titleraw`/`actionbar`/rawtext、`scoreboard players operation` 的 `><`（交换）、`*=`（乘）等运算、以及 selector 里的 `scores={传送=!0..39}`（`!` 表示「非」，即分数不在该区间）均为基岩版特有写法
- 涉及 [`/scoreboard`](../../commands/scoreboard/)、[`/execute`](../../commands/execute/)、[`/tp`](../../commands/tp/)、`/tellraw`、[`/title`](../../commands/title/)、[`/gamerule`](../../commands/gamerule/) 均需 OP 权限
- 本组指令原为「织梦菜单」系统的互传模块：入口状态 `传送菜单=5` 与列表槽位发号（`传送` 0~39）由上级菜单维护，独立使用时需自行补齐这两处（见上文说明与常见问题）
