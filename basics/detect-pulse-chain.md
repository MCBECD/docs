检测-脉冲链解决的是一个很常见的需求：**条件每刻都在检查，但动作只该执行一次。** 玩家丢出雪球要提示一句，玩家进入区域要发一次奖励，分数达标要触发一次结算——检测是持续的，动作是一次性的。

### 原理

分成两截：

- **检测**：一个重复命令方块，保持开启、延迟 0，每刻跑一次判定。它是"成功的"还是"失败的"，由命令自己决定。
- **动作**：一条脉冲链，只在检测成功的那一刻被激活一次。

两截之间靠红石比较器连接。比较器读检测方块的成功次数：检测成功，输出信号，脉冲链被激活；检测失败，没有信号，脉冲链不动。

关键在于**脉冲方块每次被激活只执行一次**，而重复方块是每刻执行。所以只要条件一直成立，检测每刻都在成功，但比较器只有从"无信号"变成"有信号"的那一下才会触发脉冲链——中间持续有信号时不会再触发。

这带来一个必须处理的问题：**信号会一直保持**。比较器读到成功次数后持续输出，直到检测失败才断电。如果下一次检测又立刻成功，中间没有断电，脉冲链就不会被再次触发。所以动作本身要把条件破坏掉——比如把雪球杀掉、把玩家传走、把分数清零。这也是这类结构常写成"检测 → 执行 → 清场"三段的原因。

### 结构

```
① 重复方块（检测）  →  ② 红石比较器（读成功次数）  →  ③ 脉冲方块 + 连锁链（动作）
```

- ① 的命令要让"命中"表现为成功，常用 `execute if entity ...` 或 `testfor`。
- ② 比较器背对 ①，可以隔一个实体方块。
- ③ 是普通脉冲链，第一块设脉冲，后面接连锁。

比较器有 **2 游戏刻延迟**，也就是动作比检测晚约 0.1 秒。绝大多数场景感觉不到；对时序极其敏感的地方改用 [`断链`](../broken-chain/)。

### 和检测-循环链的区别

| | 检测-脉冲链 | 检测-循环链 |
|---|---|---|
| 动作执行次数 | 条件成立时一次 | 条件成立期间每刻 |
| 中间件 | 红石比较器 | 无，条件方块直连 |
| 延迟 | +2 刻 | 0 |
| 适合 | 奖励、提示、传送、结算 | 持续生效的效果、计时、显示 |

检测-循环链就是不加比较器，让重复方块直接接一串条件制约的连锁方块。代价是条件成立期间动作会一直重跑，所以动作里通常要带"只做一次"的保护。

### 示例

**丢雪球只提示一次**：

<CmdRepeat>`/testfor @e[type=snowball]`

<CmdImpulse>`/say 你丢出了雪球！`

<CmdChain>`/kill @e[type=snowball]`

第一条每刻检查世界上有没有雪球，第二条是脉冲方块执行的动作，第三条把雪球清掉——不清掉，条件就一直成立，比较器不会断电，下一次丢雪球就触发不了了。

**进入区域发一次奖励**：

<CmdRepeat>`/execute if entity @a[x=100,y=64,z=100,dx=5,dy=3,dz=5]`

<CmdImpulse>`/give @a[x=100,y=64,z=100,dx=5,dy=3,dz=5] diamond 3`

<CmdChain>`/tag @a[x=100,y=64,z=100,dx=5,dy=3,dz=5] add got_reward`

要防止同一玩家反复领奖，检测条件里加 `tag=!got_reward`，第二次进来就匹配不到了。这是比"清场"更稳的写法：

<CmdRepeat>`/execute if entity @a[x=100,y=64,z=100,dx=5,dy=3,dz=5,tag=!got_reward]`

### 基岩版注意

- 比较器读命令方块时，输出强度等于成功次数，超过 15 按 15 算。信号强度不影响"有没有信号"，只影响强弱。
- 比较器可以被一个实体方块隔开，不必紧贴。
- 检测命令必须"失败即不输出"。`execute if entity` 匹配不到目标时判定失败，正好符合；`/kill @e` 这类匹配不到也会返回成功，不适合当检测。
- 检测方块的成功次数会保留上一次的值，所以别用 `/scoreboard players add` 这类永远成功的命令当检测。
